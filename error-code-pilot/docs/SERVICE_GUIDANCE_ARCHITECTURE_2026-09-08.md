# Service guidance: newcomer workflow and extension boundaries

Date: 2026-09-08. Scope: isolated Error Code specialist UI, following task 007 and the user's visual/architecture follow-up. This is a presentation extension, not a knowledge promotion or a new repair authorization.

## Implemented now

The identification flow remains a supported model and broad observable problem, followed by a filtered controlled symptom and optional error text. Necessary conditions still precede the result. No repair instructions appear during identification.

Page 2 presents the target area, numbered approved actions and an adjacent verification section on desktop. Narrow screens stack those sections. All approved action and verification text remains visible, in its original order. The fallback and existing verified-before-reporting-Fixed interaction remain. Reading an instruction is not treated as completing it, and a user-reported outcome is not a verified case closure.

`src/service-plan.mjs` is the presentation adapter between the existing authorized resolver result and the page. Its output is ordered steps, verification and fallback. `src/app.mjs` consumes that output only after the existing exact-path guard. The adapter cannot search, select, merge or authorize a repair path.

There is currently no resource provider and no part/tool/manual data connected. The application passes no support records or confirmed facts. An empty resource list produces no headings, empty cards, placeholders or coming-soon text. Existing actions remain usable to their existing documented level of detail; this release does not claim that a novice can safely perform undocumented disassembly unaided.

## Future step-level resources

| Kind | User question | Placement when approved data exists |
| --- | --- | --- |
| reasoning | Why am I checking this? | Optional explanation under the relevant action |
| tools | What do I need and how do I use it? | Tool and use instructions under that action |
| parts | Which exact part and how many? | Part number and quantity, after fitment and replacement target are established |
| disassembly | How do I access, remove and reinstall it? | Applicable procedure under the action, after prerequisites are established |
| verification | What should I see after this step? | Expected observation supplement; overall verification remains visible |

These are supplemental disclosures, not five permanent panels. Mandatory safety warnings and required operating instructions must stay visible in the approved action. They must never be hidden merely because supplemental content is collapsed.

The executable JSDoc contract in `src/service-plan.mjs` accepts a curated `StepSupport[]`. Each record includes its kind, reviewed status, scope/safety review flags, title, lines and an exact binding to card ID, path ID, actual model, firmware, knowledge version, action index and full instruction text. Parts also require a part number and positive integer quantity. Unsupported or mismatched records are omitted. Only presentation fields reach the renderer, through text nodes.

The binding deliberately uses exact equality. It does not infer family-level compatibility or treat a blank firmware value as a wildcard. The index plus full text and knowledge version prevent stale attachments when actions are reordered or rewritten. A later authored-step schema should introduce immutable step IDs and a reviewed migration before relaxing this binding.

Part records additionally require `part-fitment-confirmed` and `replacement-target-confirmed`. A likely faulty component alone is insufficient, especially where one path names several possible components. Disassembly requires `safe-to-open-confirmed` and `service-procedure-scope-confirmed`. The future publisher must derive these facts from validated applicable evidence and required confirmations. Free text, an error-code match, reading a disclosure or clicking a generic checkbox cannot establish them. No such facts are currently generated by the app.

The current review flags validate supplied records; they are not authentication or evidence of external approval. A production ingestion/review pipeline is not implemented by this interface. Required missing procedures or tools must block the affected future operation upstream and route to PIE, rather than silently dropping an essential prerequisite from an otherwise authorized instruction.

## How to connect actual resources later

1. Curate source material: obtain approved service procedures, parts/fitment records and tool requirements. Record source/version, reviewer, model and hardware/assembly revision, applicable serial ranges and firmware conditions where relevant. Separate inspection from an authorized replacement decision. Keep conflicting or missing scopes out of published supplements.
2. Publish a reviewed projection: map each resource to an exact approved path and step. Evaluate fitment, access safety and procedure prerequisites before supplying the adapter. Reject stale versions and unverified conditions. Internal references and review evidence stay outside the public projection, as they do today. The existing adapter is the integration seam; no live API route or provider has been added.
3. Release a small reviewed pilot: verify one complete newcomer journey with actual resources, then expand. Test missing, draft, conflicting, mismatched and withdrawn material, unsupported models, stale navigation, privacy and the extracted offline package. New images/manual files require an approved asset contract, packaging and content-security review; arbitrary URLs are not supported by the current text-only interface.

For a newcomer, the intended sequence is: confirm the observed problem → understand the next action → see required tools and confirmed parts when applicable → follow the approved method → compare the actual result with the expected observation → complete verification or contact PIE with the failed step. The interface supplies this structure now; source-backed procedural detail must come from the later content work.

## Visual rationale and provenance

The user explicitly requested taste-skill. The official source inspected was [Leonxlnx/taste-skill](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/SKILL.md), GitHub blob SHA `b72132fcd466da605623ffe96e370b3991fc5285`. That skill explicitly excludes multi-step product UI; only its applicable visual-audit and preserve-mode principles were used here, without replacing the business flow with a landing-page pattern.

Design intent: variance 3, motion 2, density 4. Preserve the green brand and compact native controlled selection. Unify text contrast, borders, radii and spacing; use a restrained target strip, numbered actions and a clear verification column. Keep all current approved text. No decorative imagery, dashboard panels or resource placeholders. The existing user-approved 2026-09-07 taxonomy snapshot remains a vocabulary reference, not a new knowledge authority.
